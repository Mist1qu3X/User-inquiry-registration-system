# InquiryDesk — система регистрации обращений пользователей

Учебный сквозной проект по дисциплине «Технологии разработки приложений на
базе фреймворков».

## Назначение

InquiryDesk — приложение для регистрации и учёта обращений пользователей:
приём обращения, отнесение его к категории, отслеживание статуса обработки.
Консольная версия приложения (ПР3) дополнена веб-интерфейсом на Django (ПР5).

Приложение позволяет:

* просматривать список обращений в браузере;
* просматривать карточку конкретного обращения (тема, текст, категория,
  автор, дата, статус);
* просматривать список категорий с числом обращений в каждой;
* просматривать обращения выбранной категории;
* видеть сводку обращений по статусам на главной странице;
* регистрировать обращения и изменять их статус (консольная версия);
* хранить данные между запусками приложения.

## Используемые технологии

* Python 3.10+ (проверено на Python 3.12);
* Django 5.2 — веб-фреймворк;
* HTML — разметка веб-страниц;
* CSS и Bootstrap 5.3 (подключается через CDN) — оформление страниц;
* pytest — автоматизированные тесты консольной части и модели;
* flake8 — проверка качества кода.

## Целевая аудитория

Сотрудники службы поддержки, которые принимают обращения пользователей,
распределяют их по категориям и отслеживают ход обработки.

## Предметная область

Основными объектами предметной области являются:

* пользователь — автор обращения;
* обращение — запрос пользователя;
* категория — тематический раздел обращения;
* статус — состояние обработки обращения.

Обращение относится к одной категории, имеет одного автора и один текущий
статус. Новое обращение можно зарегистрировать только в активной категории.
Финальные статусы («Решено», «Закрыто», «Отклонено») завершают обработку.

## Основные сущности

### `Category` — категория

Атрибуты: `id`, `name`, `is_active`.
Методы: `is_available()`, `from_data()`, `to_data()`, `__str__()`.

### `Status` — статус

Атрибуты: `code`, `title`, `is_final`.
Методы: `is_closing()`, `from_data()`, `to_data()`, `__str__()`.

### `User` — пользователь

Атрибуты: `id`, `name`, `email` (необязателен).
Методы: `from_data()`, `to_data()`, `__str__()`.

### `Inquiry` — обращение

Атрибуты: `id`, `subject`, `text`, `category` (объект `Category`),
`status` (объект `Status`), `author` (объект `User`), `created`.
Методы: `change_status()`, `close()`, `is_closed()`, `card()`,
`from_data()`, `to_data()`, `__str__()`.

## Страницы веб-интерфейса

| URL | View-функция | Назначение |
|-----|--------------|------------|
| `/` | `homepage.views.index` | описание приложения, сводка по статусам, навигация |
| `/inquiries/` | `inquiry.views.inquiry_list` | список обращений (сначала новые) |
| `/inquiries/<int:inquiry_id>/` | `inquiry.views.inquiry_detail` | карточка обращения |
| `/categories/` | `category.views.category_list` | список категорий и число обращений |
| `/categories/<int:category_id>/` | `category.views.category_detail` | обращения выбранной категории |

Если обращение или категория с указанным идентификатором не найдены,
страница возвращает код статуса 404. Для адресов, которым не нашлось
маршрута, при `DEBUG = False` показывается собственная страница 404
(`handler404 = "homepage.views.page_not_found"`).

## Основные операции

### Используется в веб-интерфейсе (ПР5)

* просмотр списка обращений и карточки обращения;
* просмотр категорий и обращений выбранной категории;
* сводка обращений по статусам;
* проверка, завершена ли обработка обращения (`Inquiry.is_closed()`).

### Отложено до следующих работ

Эти операции реализованы в ПР3 и работают в консольной версии. В
веб-интерфейсе они появятся, когда будут добавлены формы и POST-запросы:

* регистрация обращения (`add_inquiry()`, `can_register_inquiry()`);
* изменение статуса и закрытие обращения (`change_status()`,
  `close_inquiry()`);
* поиск обращений по теме (`find_inquiries()`);
* добавление категорий, статусов и пользователей.

## Хранение данных

Данные приложения хранятся в JSON-файлах:

* `data/users.json`;
* `data/categories.json`;
* `data/statuses.json`;
* `data/inquiries.json`.

При загрузке данные из JSON преобразуются в объекты `User`, `Category`,
`Status` и `Inquiry`; при сохранении объекты преобразуются обратно в JSON.
В `inquiries.json` связи хранятся идентификаторами `category_id`,
`status_code` и `user_id`, а при загрузке заменяются ссылками на объекты.

## Назначение модулей

### `inquirydesk/`

Пакет настроек Django-проекта:

* `settings.py` — настройки проекта (приложения, локализация, режим отладки);
* `urls.py` — маршрутизация верхнего уровня и обработчик `handler404`;
* `asgi.py`, `wsgi.py` — точки взаимодействия с сервером.

### `homepage/`

Django-приложение главной страницы:

* `views.py` — функция `page()` (общий HTML-каркас с Bootstrap и
  навигацией), `status_badge()` (цветной бейдж статуса), view-функции
  `index()` и `page_not_found()`;
* `urls.py` — маршрут главной страницы.

Функция `page()` размещена здесь, потому что главная страница задаёт общий
вид всех остальных страниц. Остальные приложения импортируют её.

### `inquiry/`

Django-приложение обращений:

* `views.py` — view-функции `inquiry_list()` и `inquiry_detail()`,
  вспомогательная функция `inquiry_items()` (список обращений в HTML);
* `urls.py` — маршруты приложения.

### `category/`

Django-приложение категорий:

* `views.py` — view-функции `category_list()` и `category_detail()`;
* `urls.py` — маршруты приложения.

Отдельное приложение для пользователей не создаётся: Django предоставляет
встроенную модель `User` (`django.contrib.auth`), работа с пользователями
будет рассмотрена в следующих темах. Статусы — справочник, поэтому они
выводятся на страницах обращений и на главной, без отдельного приложения.

Django-приложения названы в единственном числе (`inquiry`, `category`),
потому что в корне проекта уже есть модули ПР3 `inquiries.py` и
`categories.py`: пакет с тем же именем перекрыл бы модуль при импорте.

### `models/`

Классы предметной области (ПР3): `Category`, `Status`, `User`, `Inquiry`.
Не путать с файлами `models.py` Django-приложений — они пока пустые,
Django-модели появятся в следующих работах.

### `storage.py`

Загрузка и сохранение данных: JSON → объекты Python и обратно.
Функция `load_all()` (добавлена в ПР5) загружает все коллекции сразу и
используется view-функциями.

### `main.py`, `utils.py`

Консольная версия приложения и функции безопасного ввода (сохранены с ПР3).

### `tests/`

Автотесты pytest консольной части и объектной модели. Тесты веб-страниц
находятся в `tests.py` Django-приложений.

## Используемые функции ПР3 в веб-интерфейсе

| Функция | Файл | Где используется |
|---------|------|------------------|
| `load_all()` (ПР5) | `storage.py` | все view-функции |
| `sort_inquiries_by_date()` | `inquiries.py` | список обращений, страница категории |
| `find_inquiry()` | `inquiries.py` | `inquiry_detail()` |
| `filter_inquiries_by_category()` | `inquiries.py` | список и страница категории |
| `filter_inquiries_by_status()` | `inquiries.py` | сводка на главной |
| `find_category()` | `categories.py` | `category_detail()` |
| `sort_categories()` | `categories.py` | `category_list()` |
| `list_statuses()` | `statuses.py` | сводка на главной |
| `Inquiry.is_closed()` | `models/inquiry.py` | карточка обращения |
| `Category.is_available()` | `models/category.py` | категории |

## Запуск приложения

Требуется Python 3.10 или новее (Django 5.2 не поддерживает Python 3.9).

```bash
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py check
python manage.py runserver
```

После запуска открыть в браузере адрес <http://127.0.0.1:8000/>.

Консольная версия (сохранена):

```bash
python main.py
```

## Текущее состояние и план развития

Реализовано (ПР5):

* Django-проект `inquirydesk` и три Django-приложения
  (`homepage`, `inquiry`, `category`);
* маршрутизация URL двух уровней (`include()`), динамические URL с
  конвертером `<int:...>`;
* view-функции и страницы, собственная страница 404;
* отображение данных предметной области из JSON средствами ПР3;
* навигация между страницами, оформление Bootstrap 5.3.

Планируется:

* перенос сущностей в Django ORM и подключение базы данных;
* переход на шаблоны (`templates/`) и отказ от функции `page()`;
* формы регистрации обращения и изменения статуса;
* аутентификация пользователей.

## История развития

* **ПР1** — начальный консольный сценарий (три функции работы с обращениями).
* **ПР2** — модульная структура, коллекции, хранение в JSON, меню, автотесты.
* **ПР3** — объектная модель: сущности переведены из словарей в классы.
